# n169: a repair facing many failed checks acts biggest first

Found in n168 try 2 (round 42 e1 podcast): the build ran the page past the screen and nine checks failed. The repair
was handed all nine in check order, read App.tsx, main.tsx, two Globs and the vite config, and went 180 s with no
edit, so the build was kept as it was (38.9).

## What was built
- **Biggest first** (`repair-brief.ts` `failureWeight`, `rankFailures`, `failureBrief`): with 4 or more failures the
  repair is told how many there are, ranked by how much of the page each moves (pixels off, +200 when the whole page
  below is pushed or something is off the screen, +120 when nothing was built for a drawn mark; colour fixes capped
  low, since they move nothing). The top 3 are marked FIX FIRST, the rest THEN, IF QUICK, and the first Edit is asked
  for within a minute, reading nothing but the page file. Fewer than 4 failures go as before.
- **The page file is always named** to a repair, even one sent to a fresh agent (it used to be named only when the
  build's own agent was still open).
- **A stalled repair that edited nothing is retried once** (`run2.ts`): nothing on disk changed, so a fresh agent is
  told only the 3 biggest problems; the stalled turn does not use up a round. Not fired in the live tries below
  (no repair stalled); covered by the type check, not by a live run.
- 4 unit tests (`n169-repair-triage.test.ts`) on the real nine failures of n168 try 2: the page-wide sidebar drift,
  the missing player ring and the rows offset lead; the title-length nit is never first. Zero tokens.
